# AI NoC Performance Efficiency Evaluation

## Goal

For each AI communication type, compare measured performance with its analytic ideal, then select
the lowest-cost configuration that retains acceptable performance across the full workload set.
The report must separate workload sensitivity from hardware configuration trade-offs.

This specification changes the benchmark and report method only. It does not approve an RTL
parameter default change.

## Naming discipline

The report uses established quantities: Ideal Throughput Bound, Accepted Throughput, Zero-load
Latency, Saturation Throughput, Completion Time, Link Utilization, Buffer Occupancy, Speedup, and
Pareto candidates. Burst Length is a workload variable, not a DUT configuration or performance
metric. Outstanding Depth is fixed at the specified maximum of 32 transactions per initiator.
`RR` and `RRD` are the only approved project aliases and are expanded at first use as 2-channel
REQ/RSP and 3-channel REQ/RSP/DAT mappings.

## Evaluation axes

| Axis | Role | Values |
|---|---|---|
| Communication type and Read/Write direction | AI workload mapping | Existing report mappings, excluding Broadcast Read |
| Burst Length | Workload characterization | 1, 4, 16, 64 beats on the baseline DUT configuration |
| Outstanding Depth | Fixed source concurrency | 32 transactions/initiator |
| DAT VC count and Router VC depth | DUT configuration trade-off | Existing measured candidate configurations |
| Read RoB depth | DUT capacity check | Existing measured candidates; extend only if a capacity limit is observed |
| Multicast implementation | Collective comparison | Hardware multicast and repeated unicast |
| Channel mapping | Isolation comparison | RR and RRD |

`Burst Length` describes each AXI request generated by the master. Its characterization shows how
request granularity changes performance, but it does not participate in DUT configuration ranking.
`Outstanding Depth` is also a master-side workload condition. It remains fixed at 32 so every DUT
configuration is compared under the same maximum permitted source concurrency. `DAT VC count`,
`Router VC depth`, and conditionally `Read RoB depth` consume DUT resources and participate in
configuration selection. `Max Transactions/ID` remains fixed at its specified value of 32.

NI DAT TX depth is not sized to absorb the complete Outstanding window. Standard AXI ready/valid
backpressure is allowed when its existing queue is full. Keep its current depth and include its
actual storage in the cost table; open a separate depth sweep only when a TX-full admission-stall
counter shows that it limits Accepted Throughput. NI DAT RX VC depth is configured with Router VC
depth during the first comparison. The two may be separated only when per-queue occupancy proves
that one side needs different capacity.

## Common workload and timing rules

Each source-to-destination logical flow transfers 4096 B per round. A 16-round run therefore
transfers 65536 B per flow. The native DAT payload is 64 B per beat. Burst length means beats per
transaction, not `AxLEN`.

| Burst length (beats) | Transactions per 4096 B flow |
|---:|---:|
| 1 | 64 |
| 4 | 16 |
| 16 | 4 |
| 64 | 1 |

Read and Write are measured in separate runs. Read memory is prefilled before the measurement
window. All comparable runs keep the 4x4 topology, XY routing, logical payload, source/destination
mapping, endpoint-stall policy, round count, Outstanding Depth of 32, and seed unchanged.

One common workload window gates every performance counter. It starts when the first active
source may issue its first transaction and ends when the last active source completes its last B
or RLAST handshake. Reset, memory prefill, warm-up, and post-run settling cycles are excluded from
Completion Time, Delivered BW, flit counts, link utilization, stall counts, and occupancy HWM.

```text
Workload Completion Time = last active-source completion cycle - common workload start cycle
```

## Ideal and measured performance

The analytic model enumerates the actual flow mapping and XY route. A resource is identified by
physical plane and endpoint port or directed link. REQ, RSP, and DAT capacities are not added
together. The native path is Data AW/W on DAT, AR on REQ, B on RSP, and R on DAT. Multicast
enumerates the forward fork tree and CollectB join tree independently; it is not expanded into
complete unicast routes.

```text
Resource serialization cycles(r) = flits carried by resource r
                                   / capacity of resource r in flits/cycle

Ideal serialization cycles = max over all resources r of
                             Resource serialization cycles(r)

Ideal Throughput Bound (B/cycle) =
    logical payload bytes delivered / ideal serialization cycles

Accepted Throughput (B/cycle) =
    logical payload bytes accepted by consumers / common workload-window cycles

% of Ideal Throughput = Accepted Throughput at Outstanding Depth 32
                        / Ideal Throughput Bound * 100
```

`Ideal Throughput Bound` is pattern-specific: Gather is limited near its root, All-to-All spreads
traffic over more links, and Multicast can deliver one injected payload to several consumers.
Therefore one traffic type may have better absolute bandwidth while another has better throughput
efficiency. The two columns answer different questions and must be read together. NoC saturation
remains reserved for a latency-versus-offered-load curve, conventionally identified near the point
where latency reaches three times its low-load value.

The main result table uses the 64-beat reference burst and one explicitly named reference
configuration. It contains one row per communication type and direction. The sensitivity section
carries the other burst lengths so that the main table does not duplicate four rows for every
traffic type. Pareto finalists use a separate configuration-comparison table.

| Communication Type | Direction | Ideal Throughput Bound (B/cycle) | Accepted Throughput at Outstanding Depth 32 (B/cycle) | % of Ideal Throughput |
|---|---|---:|---:|---:|

Completion Time, link utilization, and buffer occupancy are diagnostics. They do not appear in
this main comparison table because their values depend on burst length and the measured configuration.

## Burst Length Characterization

Burst Length characterization measures how AXI request granularity changes NoC performance. Run
the four Burst Length values on the baseline DUT configuration with 4096 B per flow and
Outstanding Depth fixed at 32.

Interpret the evidence in this order:

1. Compare Accepted Throughput and Completion Time across Burst Length values. A short-burst loss
   identifies request and response overhead, not a DUT configuration change.
2. Attribute the limit to Read RoB or transaction slots only when the corresponding HWM reaches its
   capacity and its admission-stall counter is non-zero.
3. Evaluate a deeper Router VC buffer only when a per-input, per-VC HWM reaches capacity and an
   eligible flit is blocked because its selected VC has zero credit.
4. Evaluate more VCs only when traffic-class or packet-level head-of-line blocking is observed and
   deeper capacity alone does not remove it.

The required Router counters are project-specific diagnostics, not standard NoC metrics. The
current aggregate Router HWM and `any VC has zero credit` stall count are insufficient for this
attribution and must not be used for a buffer-depth conclusion.

Use Broadcast Global Write, Gather Global Read and Write, All-to-All Read and Write, and Pipeline
P2P Read and Write as the first screen. Expand to the remaining mappings only when two candidate
configurations cannot be separated by this screen.

## Multicast comparison

Compare hardware multicast with repeated unicast only for Broadcast Write. Both runs use the same
active producers, destination set, 4096 B delivered to every destination, burst length, round
count, Outstanding cap, AXI-ID policy, issue order, endpoint policy, and hardware configuration.
The definition of each destination set states whether the producer's local node is included. Run
Row, Column, Local 2x2, and Global destination sets.

```text
Multicast speedup = repeated-unicast Completion Time / multicast Completion Time
```

`Source injected flits` counts producer-side forward AW and W flits only. It excludes B and
CollectB traffic injected by destinations. Report Completion Time, source injected flits, speedup,
and destination count. This comparison shows the value of replication in the network without
changing the logical work. Do not introduce a separately named flit-reduction metric; the raw
flit counts remain visible.

## RR versus RRD

`RR` is the 2-channel mapping and `RRD` is the 3-channel mapping. These aliases are report labels;
the method retains the explicit mapping names. They measure channel isolation under AI traffic,
not native DAT throughput. Use 64-bit common-payload Pipeline P2P as the only AI background.
Measure Control Write with Pipeline Write and Control Read with Pipeline Read in separate runs.
Use background Outstanding Depth 32 transactions per initiator. Each Pipeline initiator uses one
AXI ID and one destination, which avoids adding a cross-destination Read-ordering policy to this
experiment.

Issue 64 single-transaction Control probes per run and report their mean Completion Time in cycles
per transaction. Start the background no later than the first probe and keep it active until the
last probe completes. RR must document a shared directed REQ or RSP resource with the Control
route. RRD must use the same geometric route edge on DAT while Control remains on REQ/RSP. A run
without the required spatial and temporal overlap is invalid.

RR/RRD uses an independent 64-bit geometry. Each AI background flow transfers 4096 B per round for
16 rounds, or 65536 B per run. One round contains two transactions of 256 beats at 8 B per beat.
Each transaction therefore uses `AxSIZE=3` and `AxLEN=255`. Outstanding Depth limits these
transactions per initiator. The Control probe remains one 8 B transaction. These runs do not use
the native 512-bit burst table above.

```text
Control latency reduction (%) = (RR latency - RRD latency) / RR latency * 100
```

The current comparison uses the same three physical networks and leaves DAT idle in RR. It cannot
claim area or power savings for a physical two-network implementation. RR/RRD results therefore do
not enter the native 512-bit bandwidth-efficiency score or final PPA ranking. A real two-network
architecture and synthesis evidence would be required for that claim.

## Configuration selection

Do not run the full Cartesian product. Use successive gates:

1. Characterize Burst Length on the current baseline DUT configuration at Outstanding Depth 32.
2. Run the existing DUT VC/depth candidates at Burst Length 64 and Outstanding Depth 32.
3. Extend Read RoB depth only when its high-water mark reaches the configured limit and a
   resource-specific non-zero admission-stall counter is observed. Keep Max Transactions/ID fixed
   at 32.
4. Run the complete communication set only on Pareto candidates.

Use Pareto dominance directly on the reported standard metrics. Compare Router DAT, NI DAT RX, NI
DAT TX, and Read RoB storage as separate objectives because their implementation costs differ. A
configuration is dominated when another measured configuration is no worse in every required
workload's Accepted Throughput and Completion Time, uses no more storage in every category, and is
strictly better in at least one reported value. Do not sum unlike storage categories or collapse
workloads into a new aggregate score.

Until performance and PPA limits are approved, output only the measured-set Pareto candidates and
do not name a final configuration. After approval, select the lowest-cost candidate that satisfies
correctness and every approved limit.

Until synthesis results exist, report these separately:

| Cost evidence | Status |
|---|---|
| Router DAT storage bits | Report per input, per router, and whole 4x4 mesh |
| NI DAT RX storage bits | VC entries * stored width; configured with Router VC depth in the first comparison |
| Read RoB storage bits | Available analytic proxy: beat slots * stored width |
| NI DAT TX storage bits | Existing queue entries * stored width; depth held fixed unless TX-full stalls limit throughput |
| Area | [TBD] synthesis result |
| Power | [TBD] synthesis result |
| Timing | [TBD] synthesis result |

No final configuration is selected until Area, Power, and Timing pass approved limits.

## Report structure

1. **Method and Workload**: fixed parameters, traffic mappings, timing window, and formulas.
2. **Performance Efficiency**: the single main table plus one Ideal-versus-Measured plot.
3. **Workload and Architecture Comparisons**: Burst Length characterization, Multicast comparison,
   and RR/RRD Control latency at Outstanding Depth 32.
4. **Configuration Trade-off**: Pareto plot, storage proxies, limiting workload, and
   `Final recommendation = [TBD]` until the selection limits are approved.

Communication and compute overlap remains a workload-specific check rather than a configuration
score. Report the two standard time quantities directly:

```text
Communication Time = Workload Completion Time
Compute Time = approved PE compute cycles for the same work
```

The report must name the PE compute workload and Compute Time used. Until an approved PE result
exists, Compute Time is `[TBD]`; no reference value is guessed. The interpretation is stated
directly: communication is fully hidden only when Communication Time is no greater than Compute
Time.

## Validity and acceptance

A result is valid only when all of these pass:

1. The scoreboard passes and all issued transactions complete.
2. Read data comes from the documented prefill image and matches expected data.
3. Compared runs deliver the same logical payload to the same consumers.
4. Analytic flit counts agree with emitted flit counters for one directed check per mode.
5. Reported units are present in every result row, and the measured configuration is stated beside
   every result table or figure.

## Method provenance

There is no single protocol standard for NoC performance reporting. This method uses published
NoC evaluation conventions and labels project-specific policies explicitly:

- The official [BookSim manual](https://github.com/booksim/booksim2/blob/master/doc/manual.tex)
  defines latency-versus-offered-load measurement with warm-up, measurement, counter reset, and
  drain phases. It does not define an Outstanding-depth saturation metric.
- Published NoC evaluation uses the point near three times zero-load latency as a saturation
  convention; see [On-Chip Network Designs for Many-Core Computational Platforms](https://vcl.ece.ucdavis.edu/pubs/theses/2012-3/atran_dissertation.pdf).
- Credit-based buffer sizing is a flow-control capacity problem; see
  [Analyzing Credit-Based Router-to-Router Flow Control for On-Chip Networks](https://doi.org/10.1587/transele.E92.C.1276).
- The multicast baseline follows the published comparison against multiple unicast in
  [A Multicast-Capable AXI Crossbar for Many-core Machine Learning Accelerators](https://arxiv.org/abs/2502.19215).
- Reporting Pareto candidates for latency, power, and network resources follows
  [Pareto-Optimization Framework for Automated Network-on-Chip Design](https://arxiv.org/abs/1807.11607).

## Out of scope

- Compute RTL or a guessed PE performance model.
- Broadcast Read.
- A full Cartesian sweep of every workload and hardware parameter.
- Frequency, area, power, or timing claims without synthesis evidence.
- Treating a larger buffer as beneficial when occupancy and stall evidence do not require it.
